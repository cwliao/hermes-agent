# GATE8-PATH-001 — how to reach acceptance gate 8

Status: proposed. Decision needed before implementation. No code changes here.

## Where gate 8 stands

Gate 8 of `HERMES-MULTI-AGENT-CLAUDE-WORKER-001`:

> the user sends the request through Telegram and directly confirms seeing the
> final synthesized response.

Every gate it depends on now passes. On 2026-08-19, after
`SWARM-E2E-DEFECTS-001` Defect 2 was fixed and deployed, the four-lane swarm
completed **unassisted** from the CLI for the first time: seven cards to
`done`, zero `blocked` / `gave_up` / `timed_out` events, no manual completion.
The previous run had reached `done` only because the operator hand-wrote the
completion contract into the worker task text; that text was removed for this
run.

Gate 8 is the only gate never executed successfully. The attempt on the same
day produced nothing — see
[TELEGRAM-SWARM-UNREACHABLE-001](2026-08-19-telegram-swarm-unreachable-001.md).

## What the gate actually requires as evidence

The plan already forecloses the obvious failure mode. From the acceptance
section:

> The goal card must close only after the synthesizer result is recorded and
> the Telegram terminal event is correlated to the same opaque goal/task
> identity. A Telegram process exit, service health, polling progress, empty
> updates, or `hermes send` success is not direct user-visible evidence.

This matters more than it did yesterday. On the same day the agent produced a
detailed report of a swarm that never ran
([FABRICATED-TOOL-SUCCESS-001](2026-08-19-fabricated-tool-success-001.md)). A
reader treating the chat reply as the signal would have recorded gate 8 as
passed. The reply was refuted by looking for the synthesizer card and finding
none — which is precisely the correlation the plan demands.

The criterion is well specified. Its **enforcement is not**: nothing in the
gate requires that the correlation actually be performed at close time. It was
performed on 2026-08-19 only because an operator went looking, and the thing
that prompted the looking was suspicion, not process. A user reading Telegram
cannot distinguish a plausible fabricated result from a real one; that is not
a defect in the user, it is a missing step in the gate.

**Any option below is verified the same way: a synthesizer card in `done` with
a non-empty `result`, correlated by task id to what the user saw.** Chat text
is never the evidence. Whether that correlation should be a scripted check
rather than an operator habit is an open question this ticket does not settle.

## The blocker

Establishing what is and is not known, per the sibling ticket: both of the
agent's tool calls failed and nothing was created; *why* they failed is not
established. Separately, and regardless of why those calls failed, the surface
has no route to a lane-bound swarm — no swarm-creation tool is registered, and
`kanban_create` cannot set the lane contract fields that `create_swarm()`
writes and `validate_completion()` enforces.

That second fact is what makes this a design decision rather than a bug fix.

## Options

### A — register a swarm-creation tool for the agent

Expose the existing `create_swarm()` as a model-facing tool, the way the CLI
`hermes kanban swarm` subcommand already does.

- Closest to what the plan describes: "a Telegram user asks Hermes to create a
  Kanban goal ... invoke every explicitly configured and authenticated worker
  lane".
- Within the plan's own boundary, which forbids adding "a dispatcher target,
  custom dashboard, provider integration, Telegram adapter, or alternate task
  store". A tool over an existing function is none of those.
- Removes the dependency on the agent composing a correct shell command. Note
  this is an architectural argument, not a claim about today's failure: the
  cause of both tool-call failures is unestablished, and if the surface drops
  or mangles tool arguments generally, a new tool fails the same way.
- Cost: a new tool surface, its schema, its argument validation, and the
  orchestrator-only gating the other board-routing tools already use. The tool
  must also default `--worker-max-runtime`; the default of 120s times out every
  worker, observed today before the operator noticed the omission.
- Depends on `TELEGRAM-SWARM-UNREACHABLE-001` Defect A being resolved, since
  the kanban toolset is gated off on this surface today. That fix is in the
  toolset gate (`tools/kanban_tools.py`) or in `toolset_validation.py`, not in
  the Telegram adapter, so it does not cross the boundary in "Not in scope".

### B — leave the terminal path and make it work

Keep shelling out to the CLI; fix whatever made both calls fail.

- Smallest change *if* the cause turns out to be configuration.
- But the cause is not established. Defect C (`terminal.timeout: 60`) is real
  and would need raising, yet raising it would not have fixed today's attempt:
  zero cards existed after the 60s the command ran, so it had not reached card
  creation. Committing to this option means first running the isolation test
  the sibling ticket proposes.
- Leaves the agent composing a multi-flag shell command each time, which is a
  standing source of the same class of failure.

### C — re-scope gate 8

Create the swarm from the CLI and require only that the synthesized result
reaches the user through Telegram.

- Verifies the delivery path, which is the half never tested.
- **This is a reduction of the acceptance criterion, not gate 8.** The plan's
  wording is that the user *sends the request* through Telegram. If chosen, it
  should be recorded as a distinct, weaker gate so the programme's status is
  not overstated.
- Only the user can make this call.

## Recommendation

**Run the isolation test first, then choose between A and B.** An earlier draft
of this ticket recommended A outright; both reviewers rejected that, and they
were right. The reasoning that killed it is the ticket's own: the isolation run
is needed whichever option is taken, and it is the only thing that would price
B correctly. Committing to the more expensive option while the information
needed to evaluate the cheaper one does not exist is a decision made early for
no gain.

The isolation test is the same request against the same agent runtime off
Telegram. It distinguishes:

- tool calls succeed off Telegram → the fault is in this surface, and **B is
  probably a configuration fix**;
- tool calls fail the same way off Telegram → the fault is in the model or the
  tool schema, and **A does not escape it either**, since a new tool would be
  dispatched through the same machinery.

Only the second outcome makes A clearly better than B, and it is also the
outcome under which A alone is insufficient.

A remains the better *architectural* fit — it matches what the plan describes
and removes a standing source of malformed shell commands. That argument is
independent of today's failure and does not require the isolation result. It
is not, on its own, a reason to skip the diagnostic.

**Neither option addresses the programme's real exposure.** Whichever is
chosen, gate 8 would pass while the fabrication defect stands: an agent whose
tool calls fail can still report success, and gate 8's correlation requirement
protects only this one gate, only when someone performs the correlation. That
is an argument for prioritising `FABRICATED-TOOL-SUCCESS-001` ahead of gate 8,
not an argument between A and B.

### Readiness

A is **not scoped**. Three interface questions below are unresolved and are
design decisions, not details. B is not scoped either, since its scope is
whatever the isolation test finds. Nothing here is ready to implement.

## Not yet decided

- Whether the swarm tool takes a worker list, or a lane list with the task text
  applied per lane. The CLI takes `PROFILE:TITLE[:SKILL,SKILL]` plus a parallel
  `--worker-lane` list, and keeping two lists in step is error-prone for a
  model.
- Whether the tool should be orchestrator-only, matching `kanban_list` and
  `kanban_unblock`, or available wherever the kanban toolset is.
- Whether it should refuse to build a graph when a lane's preflight skill is
  unavailable, or build it and let the verifier fail closed. The existing
  quorum rule (`native_hermes` plus at least two of three external lanes) has
  to be honoured either way.
- Whether gate 8 should be attempted before or after
  `FABRICATED-TOOL-SUCCESS-001` is addressed.

## Not in scope

No change to `create_swarm`, `validate_completion`, the lane quorum, the
dispatcher, or the Telegram adapter.
