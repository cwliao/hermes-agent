# SWARM-E2E-DEFECTS-001

Design and decision only. No implementation is authorized by this document.

## Why this exists

`HERMES-MULTI-AGENT-CLAUDE-WORKER-001` (PR #48) and its quorum amendment
(PR #49) were merged on code-gate evidence alone: unit tests, CI, and a
two-of-three review of a metadata-only packet. Acceptance gates 3-9 — the
ones that require actually running a lane-bound swarm — were never executed.

On 2026-08-19 the disposable four-lane joke-brainstorm test was finally run
against the deployed release (`547f82d812`, drop-in 44). It produced a
complete graph, and it surfaced four defects that no unit test, no CI run,
and no packet review had found. All four are recorded here.

Outcome summary of that run, so the defects are read in context:

- Gate 3 (runtime preflight): PASS. All four lanes resolved a CLI and a
  skill.
- Gate 4 (graph construction): PASS on the second attempt (see Defect 1).
- Gate 5 (worker completion): **PASS, but only because the operator wrote
  the completion contract into each worker's title by hand.** All four
  workers —
  `native_hermes`, `claude`, `grok`, `agy` — completed on their own with
  contract-valid metadata enforced by `kanban_db.validate_completion`. Each
  returned a real joke in its `result` field.
- Gate 6 (verifier / synthesis): **PARTIAL.** The fail-closed unlock worked
  exactly as designed — the synthesizer moved `todo -> ready` only after the
  verifier's `gate=pass` was persisted. But **neither the verifier nor the
  synthesizer agent could complete itself**; both blocked asking for operator
  help, and both were completed manually from the CLI. See Defects 2-4.
- Gates 7-9 (Dashboard evidence, Telegram user-visible delivery, cleanup):
  not attempted in that run.

The gate-5 versus gate-6 asymmetry is the central finding, but **not for the
reason first written**. An earlier draft attributed it to a skill the workers
had and the other cards lacked; checking showed no card had that skill at
all. The real difference is that the operator hand-wrote the completion
contract into the worker titles, while the verifier and synthesizer bodies —
generated by `create_swarm()` — do not state it. See Defect 2.

## Defect 1 — `create_swarm` is not atomic; a failed build leaves a live partial graph

**Severity: high.** Creates orphaned work that executes and consumes budget.

The first graph-creation attempt failed validation on the second worker:

```
kanban: worker claude requires a preflight skill id
```

That error is correct — the CLI can only infer `preflight_skill_id` when a
worker declares exactly one skill, and two had been passed. But the command
had already written cards before reaching the failing one, and they
persisted.

The board listing alone cannot show this — it carries no column tying a row
to its originating command. The parent links do. Queried after the run:

```
t_2a9b7d77   status: archived   parents: t_34572471
t_cd70205f   status: done       parents: t_6576cd95   children: t_8641170e
```

`t_34572471` is the root the **failed** command created; `t_6576cd95` is the
root of the second, successful graph. (`kanban show` omits `children:`
entirely when a card has none, which is why that line appears on
`t_cd70205f` and not on `t_2a9b7d77` — the absence is the zero, not a
truncation.) So `t_2a9b7d77` is provably a child of
the failed command's root, and it is not a parent of the verifier — the
successful graph's worker `t_cd70205f` is. The orphan had no downstream
consumer, by graph structure rather than by assertion.

That orphan was dispatched and executed. This snapshot was taken at 12:04,
**before** any worker had completed (the four workers of the second graph
finished between 12:06 and 12:13), which is why `t_cd70205f` also reads
`running` here and reads `done` in the parent-link query above:

```
✓ t_34572471  done     [failed command's root]
● t_2a9b7d77  running  [failed command's worker — no verifier will consume it]
✓ t_6576cd95  done     [second graph's root]
● t_cd70205f  running  [second graph's worker — verifier t_8641170e is its child]
```

Both orphans were then archived by hand:

```
Archived t_2a9b7d77
Archived t_34572471
```

Root cause: `create_swarm()` interleaves validation with persistence. Line
numbers in `hermes_cli/kanban_swarm.py` as of `a00f5ccb58`:

```
186  raise ValueError("lane-bound swarms require a lane_id for every worker")
196  raise ValueError(f"lane-bound swarms require the {REQUIRED_LANE_ID} lane")
200  raise ValueError(f"lane-bound swarms require at least {MIN_EXTERNAL_LANES} of "
206  root = kb.create_task(          <-- first write
263  raise ValueError(f"worker {worker_lane} requires a preflight skill id")
```

Lane-set identity is validated up front (186-200, all before any write). The
per-worker `preflight_skill_id` check is at 263, inside the worker-creation
loop — 57 lines after the root card has already been committed at 206. That
is the check that fired, and it fired after two cards existed.

Required: validate every card the graph will contain **before** writing any
of them, or wrap creation in a transaction that rolls back on failure. A
partially-built swarm must never be dispatchable.

## Defect 2 — `create_swarm()` writes verifier/synthesizer bodies that under-specify the contract the kernel enforces

**Severity: high.** Blocks the gate this programme exists to prove.

**Correction to an earlier draft of this ticket.** The first version claimed
workers succeeded because they carry a contract-documenting skill
(`kanban-worker`) that the verifier and synthesizer lack. That claim was
false, and it was asserted rather than checked. Two reviewers flagged it as
unproven; verifying it showed the opposite. The actual skills on the cards
from the run were:

```
worker native_hermes  t_cd70205f   (no skills at all)
worker claude         t_48cebb59   claude-code
worker grok           t_53d081c9   grok
worker agy            t_08a6b270   antigravity-cli
verifier              t_8641170e   requesting-code-review
synthesizer           t_f1ce2680   humanizer
```

**No card carried `kanban-worker`.** The `native_hermes` worker had no skill
whatsoever and still completed unassisted. So the skill is not what made
workers succeed, and attaching it is not the remedy.

What actually differed: **the operator hand-wrote the completion contract
into each worker's title/body when creating the swarm.** Every worker card
carried, in its own text:

> When done you MUST call the kanban completion tool to finish this task,
> with result set to the joke text and metadata role=worker, lane_id and
> preflight_skill_id copied from the swarm contract line in this task body,
> outcome=completed, verified_clean=true.

The verifier and synthesizer received no such text, because their bodies are
generated by `create_swarm()` and it does not state the contract. Here are
those generated bodies verbatim, so the counts below can be checked rather
than taken on trust.

Verifier (`t_8641170e`), first line of body:

> Review every worker handoff and blackboard update. Gate the swarm:
> complete only with metadata {"gate": "pass"} when evidence is sufficient;
> otherwise block with exact missing work.

Synthesizer (`t_f1ce2680`), first line of body:

> Synthesize the verified worker outputs into the final deliverable. Do not
> start until the verifier has passed the gate.

Both then receive the same generic block:

> ## Swarm protocol
> - Swarm root / shared blackboard: `t_6576cd95`.
> - Read sibling/parent handoffs from Kanban context before working.
> - Put machine-readable facts in completion metadata.
> - Put cross-worker notes on the root task using structured comments.

Measured against what `validate_completion()` actually requires. That
function is quoted here in full for the two roles, since the counts below
are exact and must be checkable — `role` and `root_id` are enforced in a
shared preamble before the per-role branch, which is why they appear in both
rows of the table:

```python
    role = contract.get("role")
    if metadata.get("role") != role:
        return f"swarm {role} completion requires metadata role={role!r}"
    if metadata.get("root_id") != contract.get("root_id"):
        return "swarm completion root_id does not match the task contract"
    ...
    elif role == "verifier":
        if metadata.get("gate") != "pass":
            return "verifier completion requires gate='pass'"
        expected = contract.get("expected_lane_count")
        if metadata.get("expected_lane_count") != expected:
            return "verifier completion requires the expected lane count"
        if metadata.get("verified_lane_count") != expected:
            return "verifier completion requires all expected lanes verified"
    elif role == "synthesizer":
        if metadata.get("outcome") != "completed":
            return "synthesizer completion requires outcome='completed'"
        if metadata.get("result_present") is not True or not (result or "").strip():
            return "synthesizer completion requires result_present=true and a result"
```

So verifier requires 5 keys (2 shared + 3 branch) and synthesizer requires 4
plus a non-empty task `result`. Against that:

| role | keys enforced by `validate_completion` (metadata keys, plus the task `result` check where noted) | how many the generated body names |
|---|---|---|
| verifier | `role`, `root_id`, `gate`, `expected_lane_count`, `verified_lane_count` | **1 of 5** — the body names `{"gate": "pass"}` and no other key |
| synthesizer | `role`, `root_id`, `outcome`, `result_present`, plus non-empty task `result` | **0 of 5** — body says only "Synthesize the verified worker outputs... Do not start until the verifier has passed the gate" |

The generic "## Swarm protocol" block appended to every card says only *"Put
machine-readable facts in completion metadata"* — it names no key.

This reframes the defect: **the generated verifier and synthesizer bodies
demonstrably under-specify the contract**, and the workers in this run are
not a counter-example to that — they carried operator-written instructions,
so they say nothing about what `create_swarm()` alone produces.

Whether a worker with a *bare* title would also deadlock is **untested**.
It is plausible — the generated per-worker text is the same "## Swarm
protocol" block, which names no metadata key either — but no such run was
performed, and this ticket does not claim it. Stating it as fact would repeat
round 1's error with the sign flipped. It is cheap to settle: create a
lane-bound swarm with bare worker titles and observe whether the workers
complete. That test should run before the "no role can complete
autonomously" framing is adopted anywhere.

Defect 3 in the earlier draft ("the synthesizer has the same gap") is not a
separate defect. It is the same defect, and it is folded in here.

## Defect 3 — the verifier's `root_id`-versus-parents confusion is unexplained by any document

**Severity: high.** Separated out from Defect 2 at reviewers' request, but
**not** lower-severity than it. This ticket states that fixing Defect 2
"would not, on its own, resolve" Defect 3, which makes them two independent
full blockers on the same gate. Rating this one medium would invite a reader
to fix Defect 2, expect gate 6 to become driveable, and be surprised. It is
narrower in blast radius — it affects only the verifier, whereas Defect 2
affects every generated role — but it blocks gate 6 just as completely.

The verifier did not merely fail to find the required key list. Its block
reason shows it had read the `[swarm:contract]` line, extracted the correct
`root_id`, and still could not reconcile it:

> contract on task body says root_id=t_6576cd95, but kanban_show parents list
> only shows [the four workers] — no parent t_6576cd95 visible. The verifier
> completion gate refuses every attempt with "root_id does not match the task
> contract" regardless of which root_id I pass.

The root is the **grandparent** of the verifier (root -> workers ->
verifier), so it is correctly absent from the verifier's parent list. Nothing
in the card body, the swarm-protocol block, or `kanban-worker`'s documented
metadata shape explains that the swarm root is not a parent. Fixing Defect 2
by documenting the key list would not, on its own, resolve this — the agent
needs to know the root is reachable via the contract line rather than the
parent list.

Note this is the agent's *self-report*, and no rejected tool payload was
captured. It is possible the agent never submitted a syntactically valid
attempt at all. That evidence gap is recorded in Open Questions.

## Defect 4 — the synthesizer contract requires a field the tool schema discourages

**Severity: medium.** A contradiction between two surfaces both merged in PR #48.

`kanban_db.validate_completion()` requires, for `role=synthesizer`:

```python
if metadata.get("result_present") is not True or not (result or "").strip():
    return "synthesizer completion requires result_present=true and a result"
```

— i.e. the task's `result` field must be non-empty. But the model-facing
tool schema in `tools/kanban_tools.py` describes that same field as:

> "Short result log line (**legacy field**, maps to task.result). **Use
> ``summary`` instead when possible**; this exists for compatibility with
> callers that still set --result on the CLI."

So the contract mandates a field the tool actively steers agents away from.
An agent that follows the tool's own guidance and puts its output in
`summary` cannot satisfy the synthesizer gate.

The blocked synthesizer's stated reason was different and **wrong**:

> Metadata validation requires outcome='completed' which is not in
> kanban-complete schema — cannot pass it programmatically via tool call.

That claim does not hold. The same tool schema in `tools/kanban_tools.py`
that labels `result` legacy declares `metadata` two fields earlier as:

> ```json
> "metadata": {
>     "type": "object",
>     "description": "Free-form dict of structured facts about this
>       attempt — {\"changed_files\": [...], \"tests_run\": 12,
>       \"findings\": [...]}. Surfaced to downstream workers alongside
>       ``summary``."
> }
> ```

An untyped object with a free-form description imposes no key whitelist, so
nothing in it excludes `outcome`. All four workers also passed structured
metadata through that same parameter in the same run. The agent misdiagnosed, and that misdiagnosis is
recorded because a future reader will otherwise find it in the card history
and believe it.

The `result`/`summary` conflict is real and is recorded on its own merits.
It is **not** claimed to be why this particular synthesizer died — Defect 2
(no stated contract) is the better proximate cause, and Defect 4 is the
landmine left behind once Defect 2 is fixed. Both round-1 reviewers flagged
the earlier "more likely cause" wording as overreach; it is withdrawn.

Caveat on the refutation: that `outcome` specifically would have passed is
inferred from the schema's free-form declaration plus the workers' success,
not from an observed counter-example with that exact key.

## Proposed remedies (for review, not yet authorized)

1. **Defect 1:** hoist all per-worker validation above the first
   `kb.create_task()` call. Prefer that over "or transactional" unless the
   store genuinely supports transactions — the latter is a design option,
   not a hand-wave. Add a test asserting a swarm whose Nth worker is invalid
   creates zero cards. As defence in depth, the dispatcher should also refuse
   cards belonging to an incomplete graph; that is additional to atomic
   create, not a substitute.
2. **Defect 2:** make `create_swarm()` state the required completion
   metadata in the verifier and synthesizer bodies it generates, keyed off
   the same source as `validate_completion()` so the two cannot drift.
   Attaching `kanban-worker` is **not** the remedy — the run shows the skill
   is neither present on the successful workers nor sufficient on its own,
   and adding a second skill to those cards would collide with the
   "exactly one skill" rule that `preflight_skill_id` inference relies on,
   which is the same mechanism behind Defect 1.
   Worker bodies should carry the contract too, rather than depending on
   whoever creates the swarm to type it in.
3. **Defect 3:** state in the generated verifier body that the swarm root is
   the grandparent and must be read from the `[swarm:contract]` line, not the
   parent list. Consider having the rejection message name the expected
   value, so an agent can self-correct instead of blocking.
4. **Defect 4:** keep `task.result` authoritative and fix the tool schema
   wording. `HERMES-MULTI-AGENT-CLAUDE-WORKER-001` already names `result` as
   the payload channel, and gates 7-9 read it — accepting `summary` without a
   write-through would silently strip the payload from Dashboard and
   Telegram delivery, converting a documentation defect into a delivery bug.
   Relaxing the gate instead would be a contract amendment and must be
   recorded on the source ticket, not decided here.

**Ordering matters.** 1 stops orphans; 2 and 3 make gate 6 driveable; 4
prevents the synthesizer breaking again once 2 lands. Then an unassisted
rerun before gates 7-9 are attempted.

## Evidence boundary

All IDs above are disposable test cards under tenant `e2e-fourlane-v2`,
already archived or completed. No message bodies, credentials, tokens, or
sensitive paths are recorded. The joke payloads are quoted only where needed
to show that `result` carried real content.

## Open questions

- **Evidence gap.** No tool-call traces were captured for the two blocked
  completions — only the agents' self-reported block reasons, one of which
  (the synthesizer's) is demonstrably false. A rerun should capture the
  actual rejected payloads before the agent-path diagnosis is treated as
  settled.
- Should `create_swarm()` refuse to build a lane-bound graph at all unless
  every generated body states its role's completion contract? That would make
  Defect 2 unrepresentable rather than merely fixed.
- Do `requesting-code-review` and `humanizer` teach completion rituals that
  actively conflict with the swarm contract? They were assumed neutral here;
  that was not checked.
- Gates 7-9 remain unexecuted. The Dashboard and Telegram gates were not
  reached in this run and are unaffected by these four defects, but they
  cannot be closed until a run completes without operator assistance.
